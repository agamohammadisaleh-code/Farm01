# پلتفرم مرغ‌یار

پیاده‌سازی پشته فنی هدف: **NestJS + PostgreSQL + JWT/RBAC** برای API، بسته دامنه مشترک برای وب و موبایل، اپ **Expo آفلاین‌فرست**، و داشبورد وب در فاز بعد.

```
platform/
├── packages/domain/     منطق مشترک: محاسبات رشد/FCR/هزینه، تقویم شمسی، استانداردها (بدون فریم‌ورک)
├── apps/api/            NestJS + Drizzle + PostgreSQL (PGlite در توسعه) + JWT/RBAC
├── services/ai/         سرویس Python/FastAPI: منحنی نژاد، بارگیری، هشدار زودهنگام، گفتار
├── apps/mobile/         React Native (Expo) + SQLite: آفلاین‌فرست، صف همگام‌سازی، اعلان
├── apps/web/            React + TypeScript + Tailwind + Recharts: داشبورد فارسی و RTL
├── scripts/import-legacy.mjs  انتقال داده از نسخه SQLite
├── docker-compose.yml   postgres + redis + api
└── .env.example
```

## چرا PGlite در توسعه؟

این محیط سرور PostgreSQL ندارد. به‌جای جایگزین‌کردن SQLite (که رفتار numeric، date، ایندکس یکتا و `ON CONFLICT` را تغییر می‌دهد)، از **PGlite** استفاده می‌شود: همان موتور PostgreSQL کامپایل‌شده به WebAssembly که درون Node اجرا می‌شود. نتیجه:

- مهاجرت‌ها و کوئری‌ها همان SQL تولیدی هستند که در تولید اجرا می‌شود.
- آزمون‌های یکپارچه بدون Docker اجرا می‌شوند و همان محدودیت‌های واقعی (مثلاً یکتایی `(flock_id, date)`) را می‌سنجند.
- برای تولید فقط `PG_DRIVER=postgres` و `DATABASE_URL` لازم است؛ هیچ تغییری در کد نیست.

## مدل داده

مدل دقیقاً مطابق فهرست خواسته‌شده پیاده شده است:

```
Farm(id, name, location, owner_id)
 ├─ Hall(id, farm_id, name, capacity)
 │   └─ Flock(id, hall_id, breed, start_date, initial_count, status)
 │       ├─ DailyLog(id, flock_id, date, mortality, cull, feed_kg, water_liter, avg_temp, notes)
 │       ├─ WeightSample(id, flock_id, date, sample_count, avg_weight_gr)
 │       ├─ Vaccination(id, flock_id, name, scheduled_date, done_date, status)
 │       ├─ Medication(id, flock_id, name, dose, start_date, end_date)
 │       ├─ Expense(id, flock_id, category, amount, date, description)
 │       └─ Sale(id, flock_id, date, total_weight_kg, price_per_kg, buyer)
 ├─ FeedInventory(id, farm_id, feed_type, quantity_kg, updated_at)
 └─ User(id, name, phone, role(owner|manager|worker), farm_id)
```

همه شناسه‌ها **UUID متنی** هستند: کلاینت آفلاین باید پیش از اتصال رکورد بسازد و هنگام همگام‌سازی همان شناسه را بفرستد؛ با شناسه خودافزا، همگام‌سازی نیازمند تبدیل شناسه و مدیریت تصادم می‌شد.

### افزوده‌های عمدی نسبت به فهرست بالا

هر افزوده با دلیل آمده است و هیچ‌کدام جایگزین فیلدی از خواسته نیست:

| افزوده | چرا |
|---|---|
| `daily_logs.feed_type` | بدون آن، کسر خودکار از انبار به تفکیک نوع دان (آغازین/رشد/پایانی) ممکن نیست |
| `expenses.feed_type` | تا برگرداندن خرید در ویرایش/حذف، به همان ردیف انبار بخورد |
| `flocks.name`, `status`, `closed_date`, `chick_price`, `target_*` | نام و وضعیت گله برای فهرست و بستن گله؛ قیمت جوجه و هدف، ورودی محاسبات مالی و انحراف از استاندارد |
| `medications.withdrawal_days` | دوره پرهیز دارویی؛ بدون آن نمی‌توان پیش از فروش هشدار داد |
| `users.role = vet` | نقش دامپزشک (مجوز واکسن/دارو، بدون دسترسی مالی). نقش‌های خواسته‌شده دست‌نخورده‌اند |
| `farm_members`, `farm_settings`, `refresh_tokens`, `sync_receipts` | چندمزرعه‌ای بودن، تنظیمات قیمت/هدف/منطقه زمانی، چرخش توکن و بی‌اثرکردن ارسال تکراری آفلاین |
| `deleted_at` و `updated_at` در همه جدول‌ها | حذف نرم و همگام‌سازی افزایشی با موبایل |

### قواعد کلیدی

- `daily_logs` ایندکس یکتای `(flock_id, date)` دارد؛ `POST` همان روز، **upsert** می‌کند.
- `halls` یکتای `(farm_id, name)`؛ گله فقط در سالنِ همان مزرعه ساخته می‌شود و ظرفیت سالن کنترل می‌شود.
- دسترسی به هر منبع فرزند از مسیر `flock → hall → farm` بررسی می‌شود؛ UUID گله مزرعه دیگر ۴۰۴ می‌دهد.
- مبلغ‌ها `numeric(14,0)` (ریال، بدون اعشار) و وزن/مقدار `numeric(12,2)`.

### انبار دان یک «دفتر» است

موجودی افزایشی به‌روز می‌شود: خرید `+`، مصرف روزانه `−`، اصلاح دستی `±`؛ ویرایش یک ثبت روزانه ابتدا مقدار قبلی را برمی‌گرداند و بعد مقدار جدید را کسر می‌کند، پس هیچ‌گاه دوبار کسر نمی‌شود.

موجودی **منفی مجاز است** و معنی روشنی دارد: مصرفی ثبت شده که خریدِ هم‌نوعش ثبت نشده. بریدن آن به صفر باعث می‌شود انبار بیشتر از واقعیت نشان داده شود (انتقال داده قدیمی دقیقاً همین را آشکار کرد). کمبود در شاخص‌ها به‌صورت هشدار دیده می‌شود. تنها ورودی‌های انسانی (تعیین قطعی و اصلاح دستی) منفی نمی‌شوند.

## قواعد کسب‌وکار

پنج قاعده‌ای که ستون فقرات گزارش‌ها و هشدارهاست، همه در یک جا و فقط یک بار
پیاده شده‌اند: `packages/domain/src/metrics.ts`. API، گزارش‌ها، یادآورها و سرویس
هوش مصنوعی از همین توابع تغذیه می‌شوند؛ هیچ‌کدام فرمول خودش را ندارد.

| # | قاعده | فرمول در کد | نکته‌ای که در پیاده‌سازی مهم است |
|---|---|---|---|
| ۱ | ضریب تبدیل خوراک | `FCR = totalFeedKg ÷ (liveBiomassKg + soldWeightKg)` | مخرج «وزن زنده تولیدشده» است، پس وزن فروخته‌شده هم حساب می‌شود؛ اگر فقط گله زنده را بشماریم، FCR فروش‌های جزئی را جریمه می‌کند. بدون وزن یا فروش، `fcr = null` است نه صفر. |
| ۲ | نرخ تلفات (تجمعی) | `mortalityPct = mortalityTotal ÷ initial_count × 100` | **حذف (cull) از تلفات جدا شد.** حذف تصمیم مدیریتی است، نه مرگ پرنده؛ قبلاً هر دو با هم در یک ستون جمع می‌شدند و نرخ تلفات را مصنوعی بالا می‌بردند. `cullPct` و `removalPct` (تلفات + حذف) جدا گزارش می‌شوند. |
| ۳ | قیمت تمام‌شده هر کیلو | `costPerKgLive = totalCost ÷ (liveBiomassKg + soldWeightKg)` | صورت‌کسر هزینه‌های واقعی همان گله است (جوجه، دان مصرفی، دارو، کارگر، سرباز…)، نه مبلغ خرید دان در انبار؛ مخرج همان مخرج FCR است تا دو شاخص با هم مقایسه‌پذیر بمانند. |
| ۴ | هشدار افت مصرف آب | `waterChangePct = (lastWaterL − waterBaselineL) ÷ waterBaselineL × 100` با `waterBaselineL = میانگین سه روز قبل` | مبنا میانگین **سه روز قبل** آخرین ثبت است (`logs.slice(-4, -1)`)، نه میانگین کل دوره؛ افت مصرف آب علامت هشدار بیماری است و باید نسبت به روزهای سالمِ نزدیک سنجیده شود. هشدار وقتی `waterChangePct ≤ −waterDropAlertPct`. |
| ۵ | هشدار نرخ تلفات روزانه | `dailyMortalityPct = lastDayMortality ÷ (liveBirds + lastDayMortality + lastDayCulls) × 100` | مخرج «پرندگان زنده در ابتدای همان روز» است؛ اگر پرندگان اولیه را مبنا بگیریم، در گله‌ای که بخشی فروش رفته نرخ واقعی کمتر از واقع دیده می‌شود و هشدار دیر می‌رسد. |

### آستانه‌ها در تنظیمات مزرعه

آستانه‌های قاعده‌های ۴ و ۵ سخت‌کدشده نیستند و به‌ازای هر مزرعه تنظیم می‌شوند:

| ستون `farm_settings` | پیش‌فرض | بازه مجاز | معنا |
|---|---|---|---|
| `water_drop_alert_pct` | `10.00` | ۱ تا ۹۰ | افت مصرف آب بیش از این درصد هشدار می‌دهد |
| `daily_mortality_alert_pct` | `0.50` | ۰٫۰۵ تا ۲۰ | نرخ تلفات روزانه بیش از این درصد هشدار می‌دهد |

خواندن و نوشتن با `GET` و `PATCH /api/v1/farm/settings` انجام می‌شود (فقط
`owner`/`manager`) و مقدار خارج از بازه با `400` رد می‌شود. تغییر آستانه
**بلافاصله** روی هشدارها اثر می‌گذارد، چون هشدارها ذخیره نمی‌شوند و هر بار از
داده محاسبه می‌شوند.

هشدارهای محاسبه‌شده هم در پاسخ شاخص‌ها (`alerts[]`) می‌آیند و هم در
`GET /reminders` با `kind = "alert"` تکرار می‌شوند تا کاربر یک فهرست واحد
«امروز چه کاری لازم است» ببیند، همراه با پیوند مستقیم به همان تب گله.

## یکنواختی وزن

یکنواختی = درصد قطعه‌هایی که وزنشان در بازه ±۱۰٪ میانگین است. اگر ترازو خودش
CV یا یکنواختی بدهد همان ذخیره می‌شود؛ وگرنه از کمینه/بیشینه نمونه برآورد
می‌گردد (دامنه ≈ ۴σ). رابطه پایه:

```
CV = ۱۰٪  →  z = ۰٫۱/CV  →  یکنواختی = 2Φ(z) − 1 ≈ ۶۸٪
```

قضاوت: بالای ۸۰٪ خوب، ۷۰–۸۰ متوسط، پایین‌تر ضعیف. عدد یکنواختی در شاخص‌ها،
گزارش و نمودار سری زمانی برمی‌گردد.

## یادآورها

`GET /reminders` یک فهرست واحد از «امروز چه کاری باید انجام شود» می‌دهد:

| نوع | منبع |
|---|---|
| `vaccination` | واکسن‌های سررسیدشده یا نزدیک (افق پیش‌فرض ۷ روز، قابل تنظیم) |
| `medication` | پایان دوره دارو |
| `withdrawal` | دوره پرهیز دارویی؛ تا پایان آن فروش مجاز نیست |
| `stock` | موجودی دان کمتر از آستانه `feed_alert_days` (پیش‌فرض ۳ روز مصرف) |
| `log` | ثبت روزانه جاافتاده |
| `milestone` | نزدیک شدن به سن هدف/بارگیری |
| `alert` | هشدارهای قواعد کسب‌وکار (افت آب، تلفات روزانه، FCR، دمای سالن…) با پیوند به تب مربوط |

هیچ یادآوری ذخیره نمی‌شود؛ همه از داده واقعی محاسبه می‌شوند تا با واقعیت
انحراف پیدا نکنند.

## گزارش‌ها (Excel و PDF)

| خروجی | مسیر | نکته |
|---|---|---|
| JSON | `/reports/flocks/:id` | همان داده‌ای که فایل‌ها از آن ساخته می‌شوند |
| Excel | `?format=xlsx` | ۷ برگه، راست‌به‌چپ، اعداد عددی (قابل جمع و نمودار) |
| PDF | `?format=pdf` | فونت وزیرمتن جاسازی‌شده + شکل‌دهی حروف + الگوریتم دوجهته |

PDF فارسی سه دام دارد که هر سه حل شده‌اند:

۱. **شکل حروف** — fontkit داخل pdfkit خودش حروف را می‌چسباند؛ تبدیل دوباره با
   `arabic-persian-reshaper` متن را خراب می‌کند.
۲. **ترتیب واژه‌ها** — pdfkit هر واژه را جدا می‌چیند و واژه‌ها را چپ‌به‌راست
   می‌گذارد («سلام دنیا» → «دنیا سلام»). راه‌حل: خودمان واژه‌ها را از راست
   می‌چینیم (`reports/rtl-text.ts`).
۳. **اعداد و پرانتز** — fontkit ارقام فارسی را معکوس می‌چیند («۹۲٫۹۷» → «۷۹٫۲۹»)،

   «(گرم)» جای «)گرم(» را بگیرد.

نمونه خروجی: `docs/samples/sample-flock-report.pdf` و `.xlsx`.

## هوش مصنوعی

سه قابلیت خواسته‌شده، هر سه با یک اصل: **خروجی باید قابل توضیح باشد و API
نباید به سرویس جانبی وابسته شود.** سرویس FastAPI در `services/ai` محاسبه
می‌کند؛ اگر خاموش یا کند باشد، همان محاسبه در NestJS انجام می‌شود و پاسخ
`source: "local"` می‌گیرد.

### ۱. پیش‌بینی وزن پایان دوره و تاریخ بهینه بارگیری

پیش‌بینی روی **منحنی همان نژاد گله** انجام می‌شود، نه یک منحنی ثابت:

| نژاد | وزن روز ۴۲ | منبع |
|---|---|---|
| راس ۳۰۸ | ۲۸۸۰ گرم | `packages/domain/src/breeds.ts` و `services/ai/app/breeds.py` |
| کاب ۵۰۰ | ۲۸۲۰ گرم | همان |
| هابارد | ۲۸۰۰ گرم | همان |
| آربور ایکرز | ۲۸۵۵ گرم | همان |

نژاد از نام آزاد تشخیص داده می‌شود («راس ۳۰۸»، «Ross 308»، «کاب»)؛ نژاد
ناشناخته خطا نیست، پیش‌فرض راس با یادداشت صریح به کار می‌رود. اعداد منحنی
در دو زبان با آزمون `test_breed_curves_match_typescript_package` قفل شده‌اند
تا از هم جدا نیفتند.

تاریخ بارگیری با **جدول تصمیم روزانه** انتخاب می‌شود: برای هر روز آینده،
«ارزش رشد» با «هزینه دان همان روز» (بر پایه ضریب تبدیل حاشیه‌ای منحنی نژاد)
و «هزینه فرصت تلفات» مقایسه می‌شود؛ اولین روزی که خالص منفی شد، روز
بارگیری است. جدول کامل (`breakdown`) در پاسخ API می‌آید تا عدد قابل
بررسی باشد، نه یک توصیه بی‌توضیح.

### ۲. هشدار زودهنگام بیماری

به‌جای یک آستانه روی تلفات، روند **آب، دان و تلفات** جدا سنجیده می‌شود:

|---|---|

| تلفات تجمعی | مقایسه با استاندارد سن (بدون حذف) |

### ۳. دستیار چت و صوتی فارسی

`POST /assistant/message` یک جمله فارسی می‌گیرد و **پیشنهاد** برمی‌گرداند؛
`POST /assistant/confirm` با `confirm: true` آن را ثبت می‌کند. هیچ داده‌ای
بی‌تأیید نوشته نمی‌شود.

| نوع جمله | نمونه |
|---|---|
| ثبت روزانه | «امروز ۱۲ تا تلف شد و ۹۰ کیلو دان خورد و آبش ۱۸۰ لیتر بود» |
| وزن‌گیری | «میانگین وزن ۱۲۰۰ گرم از ۵۰ نمونه» |
| هزینه | «۴ میلیون تومان دان آغازین خریدم» |
| فروش | «دیروز ۱۵۰۰ کیلو به کشتارگاه فروختم کیلویی ۹۸ هزار تومان» |
| پرسش | «مصرف آب چطور بوده؟»، «کی بارگیری کنم؟» |

نکته‌های پیاده‌سازی:

- **فهم جمله در بسته دامنه است** (`packages/domain/src/persian-intent.ts`)،
  نه در سرویس پایتون و نه در یک LLM. نتیجه: موبایل می‌تواند آفلاین جمله را
  بفهمد، هر قاعده با یک جمله آزموده می‌شود، و هیچ داده‌ای به بیرون نمی‌رود.
- عدد با رقم و با حروف هر دو خوانده می‌شود («دویست و پنجاه لیتر»).
- تاریخ نسبی و شمسی: «امروز»، «دیروز»، «۳ روز پیش»، «۱۴۰۵/۰۸/۰۲»، «۲ آبان».
- پرسش هرگز به ثبت تبدیل نمی‌شود؛ جمله ناقص با سؤال تکمیلی پاسخ می‌گیرد.
- ثبت از همان سرویس‌های فرم دستی انجام می‌شود، پس اعتبارسنجی، انبار دان و
  RBAC دقیقاً یکسان اجرا می‌شوند.

**صدا:** `POST /assistant/voice` صدای base64 را به `/assistant/transcribe`
سرویس پایتون می‌دهد. تبدیل گفتار روی سرور **اختیاری** است: با `AI_STT_URL`
(سرویس HTTP)، `faster-whisper` یا `vosk` فعال می‌شود؛ اگر هیچ‌کدام نصب
نباشد، پاسخ ۵۰۳ با پیام روشن برمی‌گردد و کلاینت به موتور گفتار دستگاه
(Web Speech API / Expo) برمی‌گردد. یعنی نبود مدل، ثبت با صدا را نمی‌بندد.

## اپ موبایل و همگام‌سازی آفلاین

`apps/mobile` یک اپ Expo (React Native + TypeScript) است با یک قاعده سخت:
**هیچ ثبت سالنی به شبکه وابسته نیست.** سه لایه دارد:

| لایه | فایل | کار |
|---|---|---|
| پایگاه‌داده محلی | `src/storage/db.ts` | SQLite: صف عملیات، ثبت‌های روزانه، گله‌ها، یادآورها |
| موتور همگام‌سازی | `src/sync/engine.ts` + `@farm/domain/offline` | صف، تلاش دوباره، ادغام، tombstone |
| اعلان‌ها | `src/notifications/register.ts` + `@farm/domain/notifications` | واکسن، پرهیز دارو، هشدار، ثبت جاافتاده |

منطق صف و برنامه اعلان‌ها **در بسته دامنه** است و در Node آزموده می‌شود؛
اپ فقط چسب شبکه و رابط کاربری است. این‌طور منطق آفلاین با تست پوشش دارد
بدون اینکه لازم باشد شبیه‌ساز گوشی اجرا شود.

### چرخه ثبت

```
کاربر ثبت می‌کند → SQLite (فوری، حتی پرواز‌حالت) → نوار «در صف»
      ↓ (هر ۶۰ ثانیه، بازگشت به اپ، یا دکمه دستی)
push صف → پاسخ سرور → موفق/تکراری حذف، ناموفق با تأخیر پله‌ای
      ↓
pull افزایشی از lastServerTime → ادغام بر اساس updated_at → حذف tombstone
```

`POST /sync/push` بدنه `{ operations: [{ clientId, type, flockId, payload }] }`
و پاسخ `{ serverTime, results: [{ clientId, status, entityId?, error? }], applied, duplicates, failed }` دارد.
`type` یکی از `log.save`، `weight.create`، `expense.create`، `sale.create` است.

`GET /sync/pull?since=ISO` همه داده مزرعه را با `deleted` می‌دهد (سالن‌ها،
گله‌ها، ثبت‌ها، وزن‌ها، هزینه‌ها، فروش‌ها، تنظیمات) — بدون `since`، همگام‌سازی
کامل. مسیر `metaOnly=1` فقط زمان سرور را می‌دهد.

### تضمین‌های ضد گم‌شدن و ضد تکرار

- **idempotency واقعی:** سرور برای هر عملیات «رسید» در جدول `sync_receipts`
  ثبت می‌کند. ارسال دوباره همان `clientId` پاسخ `duplicate` می‌گیرد، نه رکورد
  دوم. اگر گوشی وسط ارسال خاموش شود و صف دوباره فرستاده شود، داده دوبار ثبت
  نمی‌شود.
- **ثبت روزانه یک رکورد در روز:** کلید جدول محلی «گله + تاریخ» است (نه شناسه
  سرور) و سرور هم upsert می‌کند؛ پس ثبت دستی همان روز با رکورد همگام‌شده
  تصادم نمی‌کند و رکورد دوم ساخته نمی‌شود. صف هم عملیات‌های هم‌روز یک گله را
  با نگه‌داشتن `clientId` اول ادغام می‌کند تا نسخه در پرواز هم شناسایی شود.
- **تلاش دوباره پله‌ای:** ۲ ثانیه، ۱۵ ثانیه، ۱ دقیقه، ۵ دقیقه، ۱۵ دقیقه. بعد
  از ۵ شکست، عملیات «گیرکرده» می‌شود و **خودکار** دوباره نمی‌رود؛ در تب «صف»
  با پیام فارسی سرور و دو دکمه «تلاش دوباره» / «حذف» به کاربر نشان داده
  می‌شود. سرور را با داده نامعتبر پر نمی‌کنیم و داده کاربر را هم بی‌صدا
  دور نمی‌ریزیم.
- **خطای شبکه ≠ خطای داده:** قطع اینترنت، تعداد تلاش را مصرف نمی‌کند؛ صف
  دست‌نخورده می‌ماند.
- **حذف با tombstone:** حذف‌ها با `deleted: true` منتشر می‌شوند تا گوشی دوم
  هم حذف را ببیند (و حذف‌شده دوباره بالا نیاید).
- **تعارض:** `updated_at` جدیدتر برنده است؛ ثبتِ در صف همیشه برنده است و تا
  ارسال‌شدن با نسخه سرور بازنویسی نمی‌شود. این تصمیم در
  `decideLogMerge` (بسته دامنه) متمرکز و با سه تست پوشش داده شده است:
  حذف سرور → حذف محلی، ثبت در صف → محلی می‌ماند، نسخه قدیمی‌تر → نادیده.

### دسترسی بر اساس نقش

ماتریس دسترسی یک‌بار در `packages/domain/src/permissions.ts` تعریف شده و
API، وب و موبایل هر سه از همان استفاده می‌کنند. موبایل آفلاین است، پس
نمی‌تواند برای فهمیدن مجوز خود به سرور تکیه کند:

```
can("worker", "log:write")   → true
can("worker", "cost:write")  → false   (کارگر: دکمه هزینه ندارد)
can("vet",    "sale:write")  → false   (دامپزشک: ثبت روزانه دارد، فروش نه)
can("owner",  "member:manage") → true
```

هر عملیات صف **جداگانه** در سرور بررسی می‌شود؛ اگر گوشی دستکاری شده باشد یا
نسخه قدیمی مجوز را اشتباه نشان داده باشد، پاسخ همان عملیات `failed` با پیام
فارسی است («ثبت هزینه فقط برای مالک و مدیر مجاز است.») و بقیه صف ادامه
می‌یابد. یک خطا کل صف را متوقف نمی‌کند.

### نوتیفیکیشن

اعلان‌ها **محلی** زمان‌بندی می‌شوند (expo-notifications)، نه با سرور؛ چون
مرغدار در سالن اینترنت ندارد و اعلان واکسن فردا نباید به شبکه وابسته باشد.
سرور فقط فهرست یادآورها را می‌دهد، زمان‌بندی با `planNotifications` در گوشی
انجام می‌شود:

- سکوت شبانه ۲۲:۰۰ تا ۰۷:۰۰؛ هشدار بحرانی در همان ۰۷:۰۰ صبح، نه ۰۹:۰۰.
- واکسن: یک روز قبل، ساعت ۹ صبح.
- دوره پرهیز دارویی: روز آزادشدن فروش، ساعت ۸.
- ثبت جاافتاده: همان روز ۲۰:۰۰، وگرنه ۹ صبح فردا.
- هشدار بحرانی: بلافاصله (با رعایت سکوت شبانه).
- افق ۱۴ روز، حداکثر ۴۰ اعلان.

### فرم سریع ثبت

`src/screens/QuickLogScreen.tsx`: چهار کاشی بزرگ (تلفات، دان، آب، دما) با
آیکون، صفحه‌کلید عددی فارسی خودِ اپ (دکمه ۶۸ نقطه‌ای برای کار با دستکش)،
انتخاب «امروز/دیروز» و ورود یک‌دستی. عدد فارسی («۱۸۰») همان‌جا به عدد لاتین
تبدیل می‌شود، و اگر همان روز قبلاً ثبت شده باشد، مقدار قبلی نشان داده
می‌شود و ثبت جدید جایگزینش می‌شود — بدون ساختن رکورد دوم.

### اجرا

```bash
npm run typecheck:mobile      # بررسی نوع‌ها (همین در CI هم اجرا می‌شود)
npm run start:mobile          # expo start — اسکن QR با Expo Go
```

آدرس API در `apps/mobile/app.json` → `expo.extra.apiUrl` است (پیش‌فرض

**محدودیت صادقانه:** اپ در این محیط (بدون شبیه‌ساز اندروید/iOS) روی دستگاه

## رابط کاربری: فارسی، RTL، وزیرمتن

`apps/web` داشبورد مدیریتی است و `apps/mobile` اپ سالن؛ هر دو فارسی و
راست‌به‌چپ‌اند و از بسته دامنه مشترک می‌خوانند، تا عددی که در داشبورد دیده
می‌شود همان عددی باشد که در گوشی ثبت شده است.

### سه اصل طراحی

۱. **فارسی و RTL واقعی، نه ترجمه.** `dir="rtl"` روی `<html>`، واحدها فارسی
(کیلوگرم، تومان)، تاریخ شمسی از `@farm/domain`، و همه اعداد با ارقام فارسی
(`Intl.NumberFormat("fa-IR")`). محور افقی نمودارها هم راست‌به‌چپ است تا زمان
مثل متن از راست شروع شود.

۲. **خوانا برای سالن، نه برای آزمایشگاه.** اندازه پایه ۱۷px، هدف لمسی
حداقل ۴۴–۶۰ نقطه، کنتراست بالا و فونت **وزیرمتن** (نسخه متغیر، از پکیج
`vazirmatn` روی npm — بدون CDN، پس بدون وابستگی به اینترنت بیرونی).
اعداد `tabular-nums` هستند تا کارت‌های آماری با تغییر مقدار نلرزند.

۳. **کمترین آموزش.** کارگر سالن فقط دو چیز می‌بیند: «امروز» و «خروج».
مالک و مدیر یک تب اضافه دارند: «داشبورد». منو از ماتریس دسترسی
`packages/domain/src/permissions.ts` ساخته می‌شود، پس دکمه‌ای که دیده
نمی‌شود، در سرور هم پذیرفته نمی‌شود.

### داشبورد: چهار KPI با مرجع مقایسه

هر شاخص «چرا این رنگ است» را نشان می‌دهد؛ عدد بدون مرجع، تصمیم نمی‌سازد:

| شاخص | نمایش | مرجع مقایسه | سبز / زرد / قرمز |
|---|---|---|---|
| FCR | ۱٫۵۸ | استاندارد نژاد در سن گله | ≤ استاندارد / تا ۵٪ بالاتر / بیشتر |
| تلفات و حذف | ۱٫۹٪ | منحنی تلفات مجاز همان سن | ≤ مجاز / تا ۲۵٪ بالاتر / بیشتر |
| میانگین وزن | ۱٫۴۳ کیلو | استاندارد نژاد در همان روز | ≥ استاندارد / تا ۳٪ کمتر / کمتر |
| بهای تمام‌شده هر کیلو | ۷۹٬۴۰۷ تومان | قیمت بازار روز | ≤ بازار / تا بازار / بیشتر از بازار |

زیر آن‌ها چهار آمار عملیاتی (سود پیش‌بینی پایان دوره، دان مصرفی امروز،
موجودی دان و روزهای کافی، روزهای تا بارگیری) و بعد هشدارها می‌آیند. هر
هشدار دو بخش دارد: «چه شد» و **«چه کار کنم؟»** — توصیه پنهان نمی‌شود.

### نمودارهای روند (Recharts)

- **مصرف دان:** ستون = مصرف واقعی، خط‌چین = انتظار استاندارد نژاد.
- **وزن:** خط = وزن گله، خط‌چین = استاندارد؛ فقط تا آخرین وزن‌گیری معتبر.
- **تلفات:** ستون = تلفات روز، خط = درصد تجمعی از کل جوجه‌ریزی.
- زیر هر نمودار یک جمله‌ی ساده می‌آید («آخرین روز ۸۵ کیلوگرم — ۸٫۹٪ کمتر از
  استاندارد») تا کسی که فرصت خواندن محورها را ندارد هم بفهمد.

بخش چهارم داشبورد: ترکیب هزینه (نوار سهم هر قلم)، پیش‌بینی پایان دوره و
جدول گله‌های بسته‌شده با سود واقعی.

### صفحه «امروز» برای کارگر

چهار کاشی بزرگ (تلفات، دان، آب، دما) که با دکمه‌های **+ / −** و گام مشخص پر
می‌شوند؛ نیازی به تایپ نیست. ورودی، ارقام فارسی و لاتین را هر دو می‌پذیرد
(«۳» و «3» یک معنا دارند). اگر برای امروز قبلاً ثبت شده باشد، همان مقدارها
پیش‌پر می‌شوند و دکمه به «به‌روزرسانی ثبت امروز» تغییر می‌کند — پس ثبت
تکراری ساخته نمی‌شود. کنار فیلد دان نوشته می‌شود «انتظار امروز حدود ۱٬۸۲۴
کیلوگرم» تا کاربر بدون هیچ آموزشی بداند چه عددی معقول است.

### دسترسی و حریم

- منو و مسیرها بر اساس همان ماتریس نقش ساخته می‌شوند (`perm`).
- مهم‌تر: **API هم داده مالی را برای کارگر و دامپزشک حذف می‌کند**
  (`/analytics/overview` و `/analytics/flocks/:id`). پنهان‌کردن در رابط
  کاربری، امنیت نیست؛ اگر داده به مرورگر نرسد، قابل دیدن نیست.

### اجرا و پیکربندی

```bash
npm run build:domain            # بسته مشترک باید ساخته شود
VITE_API_TARGET=http://127.0.0.1:4000 npm run dev:web
```

مرورگر همیشه به `/api/v1` نسبی درخواست می‌دهد و Vite (توسعه) یا nginx (تولید)
آن را پروکسی می‌کند؛ بنابراین نه CORS لازم است، نه آدرس سرور در باندل
سخت‌کد می‌شود. در تولید:

```bash
npm run build:web               # خروجی: apps/web/dist
```

> **نکته ورک‌اسپیس:** `react` و `react-dom` در ریشه هم قفل شده‌اند. Expo نسخه
> ۱۸٫۲ خودش را زیر `apps/mobile` نگه می‌دارد و بدون این قفل، دو نسخه React در
> درخت می‌ماند و خطای «Invalid hook call» می‌دهد.

### آزمون‌ها

۲۲ تست در `apps/web`:

- ۱۹ تست منطق خالص: قالب‌بندی فارسی (ارقام، تومان، وزن، تاریخ شمسی، تبدیل
  ورودی کاربر)، شاخص‌ها و رنگ‌بندی‌شان، دسترسی منو برای چهار نقش، و آماده‌سازی
  سری نمودارها (مرتب‌سازی، تلفات تجمعی، خلاصه‌ها).
- ۳ تست رندر واقعی با jsdom: داشبورد با داده API رندر می‌شود و چهار شاخص و
  سه نمودار دیده می‌شوند؛ کارگر لینک داشبورد را **نمی‌بیند**؛ و ثبت فرم،
  درخواست درستی (`date`, `mortality`, `feedKg`) به API می‌فرستد.

## آزمون‌ها

```bash
npm test          # ۹۹ تست دامنه + ۱۰۵ تست API + ۲۲ تست وب
cd services/ai && python -m pytest -q   # ۲۳ تست سرویس تحلیل
```

آزمون‌های API روی PGlite اجرا می‌شوند و این موارد را می‌سنجند: ثبت‌نام/ورود/چرخش توکن، ۴۰۱ بدون توکن، ماتریس RBAC، upsert ثبت روزانه، رد تاریخ آینده و تلفات بیش از موجودی، ظرفیت سالن و رد سالن مزرعه دیگر، وزن‌گیری نمونه‌ای و استفاده از آن به‌عنوان منبع وزن، وضعیت مؤثر واکسن (شامل `overdue`)، دوره پرهیز دارو، و حسابداری انبار (خرید، کسر مصرف، ویرایش بدون کسر دوباره، منفی‌شدن در کمبود، رد اصلاح دستی منفی)، جداسازی داده دو مزرعه، و پنج قاعده کسب‌وکار (هشدار آب و تلفات روزانه از داده واقعی، اثر تغییر آستانه، اعتبارسنجی بازه آستانه، و دیده‌شدن هشدار در `/reminders`).

هشت تست همگام‌سازی آفلاین هم در همین مجموعه‌اند: ثبت عملیات صف، ارسال دوباره و
گرفتن `duplicate` بدون رکورد دوم، ادامه صف وقتی یک عملیات رد می‌شود، تفکیک
مجوز کارگر (ثبت روزانه دارد، هزینه ندارد)، دریافت افزایشی (`since`) که چیزی
برنمی‌گرداند وقتی تغییری نیست، و رسیدن حذف به‌شکل tombstone.

> آزمون‌ها با `tsc` کامپایل و سپس با `node --test` اجرا می‌شوند؛ دلیل: `emitDecoratorMetadata` که DI نشات به آن وابسته است در esbuild/tsx پشتیبانی نمی‌شود و PGlite هم داخل VM جست قابل بارگذاری نیست.

### نتیجه انتقال داده واقعی

انتقال داده نمونه موجود (`data/farm.db`) به API جدید انجام و صحت آن بررسی شد:

| مورد | مقدار |
|---|---|
| گله‌ها | ۳ (۲ فعال، ۱ بسته) |
| سالن‌ها | ۳ (از ستون «سالن» هر گله ساخته شد) |
| ثبت روزانه | ۹۶ |
| وزن‌گیری | ۳۰ (از وزن‌های ثبت‌شده در لاگ قدیمی) |
| هزینه | ۴۲ از ۴۶ |
| فروش | ۲ |
| قطعه زنده | ۱۹٬۶۳۰ — دقیقاً برابر نسخه قدیمی |
| سود تحقق‌یافته | ۳۰۰٬۵۸۰٬۲۲۳ ریال — دقیقاً برابر نسخه قدیمی |
| انبار دان | ۱۰٬۹۶۰٫۶ + ۱۰٬۳۵۶٫۵ − ۲۶٬۰۱۹٫۱ = **−۴٬۷۰۲ کیلوگرم** = خرید ۸۹٬۶۱۹ − مصرف ۹۴٬۳۲۱ |

**۴ هزینه منتقل نشد** چون تاریخشان آینده بود (۲۰۲۶-۱۰-۲۴ تا ۲۰۲۶-۱۱-۰۳). نسخه قدیمی اجازه ثبت تاریخ آینده می‌داد؛ API جدید آن را رد می‌کند. اسکریپت این موارد را گزارش می‌دهد و متوقف نمی‌شود.

اجرای دوباره اسکریپت **هیچ رکورد تکراری نمی‌سازد** (تطبیق گله با نام + تاریخ شروع، هزینه/فروش با شمارش چندتایی، ثبت روزانه با upsert، وزن‌گیری با تاریخ).

موجودی منفیِ «دان پایانی» یک واقعیت داده است، نه باگ: در نسخه قدیمی مصرف دان پایانی ۵۰٬۲۲۳ کیلوگرم ثبت شده ولی خرید هم‌نوعش فقط ۲۴٬۲۰۴ کیلوگرم بوده. سیستم آن را پنهان نمی‌کند تا مالک بتواند خریدهای ثبت‌نشده را اصلاح کند.
