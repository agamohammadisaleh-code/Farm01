قانون‌های معماری (آنچه هرگز نقض نمی‌شود)

۱. محاسبه یک‌جا، نمایش چندجا. فرمول FCR، منحنی استاندارد نژاد، هزینه هر کیلو، سهم تلفات مجاز و قواعد هشدار فقط در packages/domain نوشته شده‌اند. API همان کد را اجرا می‌کند، وب و موبایل هم همان را برای نمایش/پیش‌بینی محلی می‌خوانند. نتیجه: عدد داشبورد، عدد PDF و عدد گوشی هرگز با هم اختلاف ندارند.

۲. API هرگز به سرویس AI وابسته نیست. apps/api اول سرویس پایتون را با مهلت کوتاه صدا می‌زند؛ اگر جواب نداد یا کند بود، همان محاسبه را با بسته دامنه انجام می‌دهد و پاسخ را با fallback: true برمی‌گرداند. قطعی AI نباید ثبت داده یا دیدن داشبورد را متوقف کند.

۳. موبایل آفلاین‌فرست است. نوشتن در SQLite گوشی «موفق» است؛ ارسال به سرور کار پس‌زمینه است. صف عملیات idempotent است (sync_receipts) و تعارض با updated_at و وضعیت «در صف» حل می‌شود.

۴. دسترسی در سرور اعمال می‌شود، نه در رابط کاربری. ماتریس نقش در بسته دامنه است (تا موبایل آفلاین هم بداند)، اما تصمیم نهایی با RolesGuard در API است و داده مالی برای نقش‌های بدون cost:read حتی از پاسخ حذف می‌شود.

۵. داده حذف نمی‌شود، علامت می‌خورد. deleted_at + updated_at در همه جدول‌های عملیاتی؛ هم برای بازیابی، هم برای رساندن «حذف» به گوشی‌های دیگر.

تصمیم‌های مهم

۱. واحد پول: تومان، بدون اعشار. همه مبالغ numeric(14,0)؛ وزن‌ها و کمیت‌ها numeric(12,2). دلیل: ریال در عمل سه صفر اضافه و منبع خطای گزارش است.

۲. یک ثبت روزانه برای هر (گله، تاریخ). هم ایندکس یکتا، هم upsert سمت سرور، هم کلید محلی گوشی (نه شناسه سرور) — تا «ثبت امروز دوباره» رکورد دوم نسازد.

۳. حذف نرم + updated_at در همه جدول‌های عملیاتی. ستون‌های deleted_at/updated_at مبنای همگام‌سازی افزایشی (since) هستند.

۴. farm_settings آستانه‌ها را نگه می‌دارد. daily_mortality_alert_pct (پیش‌فرض ۰٫۵)، water_drop_alert_pct (پیش‌فرض ۱۰)، قیمت بازار و دان، timezone. هشدارها از همین‌ها ساخته می‌شوند و قابل تنظیم‌اند.

۵. sync_receipts کلید اصلی امنیت داده آفلاین است. برای هر عملیات (client_id) یک ردیف؛ اگر همان عملیات دوباره برسد، پاسخ duplicate می‌گیرد.

۶. کلیدهای خارجی با ON DELETE CASCADE برای داده فرزند و RESTRICT/NO ACTION برای موجودیت‌های مرجع. حذف گله، ثبت‌هایش را می‌برد؛ حذف کاربری که ثبت دارد مسدود می‌شود.

model DailyLog {
  id         String    @id @default(uuid())
  flockId    String    @map("flock_id")
  date       DateTime  @db.Date
  mortality  Int       @default(0)
  cull       Int       @default(0)
  feedKg     Decimal   @map("feed_kg")      @db.Decimal(12, 2)
  waterLiter Decimal   @map("water_liter")  @db.Decimal(12, 2)
  avgTemp    Decimal?  @map("avg_temp")     @db.Decimal(5, 1)
  deletedAt  DateTime? @map("deleted_at")
  flock      Flock     @relation(fields: [flockId], references: [id], onDelete: Cascade)
  @@unique([flockId, date])
  @@map("daily_logs")
}

۴.۱. ثبت روزانه (apps/api/src/logs/logs.service.ts)

مسئله: کارگر روزی یک‌بار ثبت می‌کند، ولی گاهی دوباره (اصلاح عدد) ثبت می‌کند؛ ممکن است دو گوشی هم‌زمان بفرستند. ثبت تکراری نباید رکورد دوم بسازد و نباید موجودی انبار را دوبار کم کند.

async save(farmId: string, userId: string, flockId: string, dto: SaveLogDto, timezone = "Asia/Tehran") {
  const flock = await this.access.require(farmId, flockId);   // گله متعلق به همین مزرعه؟
  const today = todayIso(timezone);
  const errors: Record<string, string> = {};

  if (dto.date > today) errors.date = "ثبت تاریخ آینده مجاز نیست.";
  if (dto.date < flock.start_date) errors.date = "تاریخ پیش از جوجه‌ریزی گله است.";
  if (flock.closed_date && dto.date > flock.closed_date)
    errors.date = "گله بسته شده و ثبت تاریخ بعد از آن مجاز نیست.";

  const existing = await this.db.select().from(dailyLogs)
    .where(and(eq(dailyLogs.flockId, flockId), eq(dailyLogs.date, dto.date))).limit(1);

  const liveBefore = await this.liveBirdsAt(farmId, flockId, dto.date);
  const lostNow = dto.mortality + (dto.cull ?? 0);
  if (lostNow > liveBefore)
    errors.mortality = `تلفات و حذف از تعداد زنده (${liveBefore} قطعه) بیشتر است.`;
  assertValid(errors, "ثبت انجام نشد؛ مقادیر را بررسی کنید.");

  await this.db.transaction(async (tx: any) => {
    if (previous) {
      await tx.update(dailyLogs).set({ ...values, deletedAt: null, updatedAt: new Date() })
        .where(eq(dailyLogs.id, previous.id));
    } else {
      // clientId از گوشی = شناسه رکورد؛ ارسال دوباره صف همان رکورد را می‌نویسد
      const id = dto.clientId && /^[0-9a-zA-Z_-]{8,64}$/.test(dto.clientId) ? dto.clientId : randomUUID();
      await tx.insert(dailyLogs).values({ id, ...values })
        .onConflictDoUpdate({ target: [dailyLogs.flockId, dailyLogs.date], set: { ...values, updatedAt: new Date() } });
    }

    // انبار: برگرداندن مصرف قبلی، کسر مصرف جدید — ویرایش، موجودی را دوبار کم نمی‌کند
    if (previous && !previous.deletedAt) {
      await this.inventory.add(tx, farmId, previous.feedType ?? feedType, n(previous.feedKg));
    }
    await this.inventory.add(tx, farmId, feedType, -dto.feedKg);
  });

  const saved = await this.db.select().from(dailyLogs)
    .where(and(eq(dailyLogs.flockId, flockId), eq(dailyLogs.date, dto.date))).limit(1);
  return { ...toLog(saved[0]), updated: Boolean(previous) };
}

۴.۲. محاسبه FCR (packages/domain/src/metrics.ts)

مسئله: FCR یعنی چند کیلو دان برای چند کیلو رشد. اگر «وزن زنده فعلی» تنها مخرج باشد، هر فروش میان‌دوره‌ای FCR را مصنوعاً بدتر نشان می‌دهد.

۸. محدودیت‌ها

این بخش پاسخ «بخش ۱۰» صورت مسئله است: کد تمیز/ماژولار/مستند، امنیت (اعتبارسنجی ورودی، RBAC، رمزنگاری گذرواژه) و مقیاس‌پذیری برای چند فارم و چند کاربر همزمان. هر ادعا با نشانی در کد یا خروجی اجراشدنی همراه است؛ جاهایی هم که ضعف داریم، به‌جای تعریف، با شدت و برنامه رفع آمده‌اند.

۸٫۲٫۲. RBAC — کنترل دسترسی مبتنی بر نقش

دو نگهبان زنجیره‌ای روی همه مسیرهای کسب‌وکار: JwtAuthGuard (هویت) و RolesGuard (اجازه). نگهبان نقش، فهرست نقش‌های مجاز را از متادیتای @Roles می‌خواند و در نبود آن، مسیر را برای هر کاربر واردشده باز می‌گذارد — دقیقاً به همین دلیل، قاعده «هر مسیر تصمیم نقش» ماشینی بررسی می‌شود.

const required = this.reflector.getAllAndOverride<Role[]>(ROLES_KEY, [
  context.getHandler(),
  context.getClass(),
]);
if (!required || required.length === 0) return true;

const role = context.switchToHttp().getRequest<AuthedRequest>().user?.role;
if (!role || !required.includes(role)) {
  throw new ForbiddenException("نقش شما اجازه این عملیات را ندارد.");
}

پوشش امروز: از ۷۴ مسیر، ۶۵ مسیر تصمیم نقش دارند؛ ۹ مسیر باقی‌مانده عامدانه است و در اسکریپت با دلیل فهرست شده: چهار مسیر عمومی احراز هویت (register, login, refresh, logout)، چهار مسیر شخصی هر کاربر (me, PATCH me, change-password, switch-farm) و GET /health.

چهار نقش داریم: owner، manager، worker، vet — با یک تفاوت مهم نسبت به ماتریس بخش ۵: نقش‌ها فقط دروازه مسیر نیستند، فیلدها را هم می‌بُرند. analytics/overview برای نقش‌های محدود، فیلدهای مالی را از پاسخ حذف می‌کند تا کارگر عدد سود را نبیند، حتی اگر مسیر را صدا بزند.

جلوگیری از بالا آمدن ناامن. مقادیر پیش‌فرض توسعه (رمز JWT نمونه و CORS باز) اگر در تولید بالا بیایند، برنامه به‌جای «کار کردن با تنظیم ناامن» همان لحظه شکست می‌خورد:

if (isProduction && (secret === "" || secret === "dev-only-secret-change-me" || secret.length < 32))
  problems.push("JWT_SECRET تنظیم نشده یا کوتاه است (حداقل ۳۲ نویسه).");
if (isProduction && (origins.trim() === "" || origins.split(",").some((o) => o.trim() === "*")))
  problems.push("CORS_ORIGINS در تولید باید فهرست دقیق دامنه‌ها باشد، نه خالی و نه *.");

لایه‌های دیگر: helmet (CSP، X-Content-Type-Options، frame-ancestors — و بازشدن آگاهانه فقط در حالت نمایشی)، CORS با فهرست سفید از CORS_ORIGINS، و docker-compose.yml که JWT_SECRET را با ${JWT_SECRET:?...} الزامی می‌کند.

۸٫۲٫۴. محدودسازی نرخ درخواست (تازه در این بخش)

پیش از این بخش، هیچ سقفی روی درخواست‌ها نبود: هر ورود یک bcrypt هزینه‌بر اجرا می‌کند و یک اسکریپت ساده می‌توانست هم گذرواژه حدس بزند و هم CPU سرور را اشباع کند. اکنون common/rate-limit.ts با الگوی «پنجره ثابت» این سقف‌ها را می‌گذارد:

استفاده در کنترلر یک خط است و سقف کنار مسیر می‌ماند:

و بلافاصله پس از قفل‌شدن آن حساب، ورود حساب دیگر همان ماشین با ۲۰۰ پاسخ می‌گیرد (آزمون e2e «قفل یک حساب، ورود حساب دیگر را نمی‌بندد»).

انبار شمارنده، خودکار انتخاب می‌شود. رابط RateLimitStore دو پیاده‌سازی دارد:

انبار کِی فعال است ویژگی

RedisRateLimitStore با REDIS_URL INCR + PEXPIRE؛ یک سهمیه مشترک برای همه نمونه‌ها

اگر Redis در دسترس نباشد، connectRedis() یک بار هشدار می‌دهد و همان لحظه به حالت حافظه برمی‌گردد؛ یعنی Redis «بهبود» است نه پیش‌شرط اجرای API. آزمون‌ها هم با یک کلاینت ساختگی همین دو مسیر (شمارنده مشترک، و بازگشت به حافظه هنگام قطع اتصال) را می‌سنجند، بدون نیاز به سرور Redis در CI.

۸٫۲٫۵. جداسازی مزرعه‌ها (چند مستأجر)

شناسه مزرعه فقط از توکن خوانده می‌شود (@CurrentUser()), نه از بدنه یا کوئری؛ بنابراین کاربر نمی‌تواند مزرعه دیگری را «صدا بزند». هر دسترسی از مسیر گله با FlockAccess.require(farmId, flockId) مشتق می‌شود و پاسخ نبودِ دسترسی 404 است نه 403 تا وجود یا نبودِ شناسه هم لو نرود. آزمون یکپارچه «تنظیمات و جداسازی مزرعه‌ها» دقیقاً همین را می‌سنجد: کاربر مزرعه دوم با توکن معتبر خودش به گله مزرعه اول ۴۰۴ می‌گیرد.

۸٫۳٫۲. همزمانی و درستی داده

  • ۱۱ تراکنش روی عملیات چندجدولی (logs.save، flocks.close، farms.create، expenses، ثبت‌نام و…). ویرایش یک ثبت روزانه، انبار را برمی‌گرداند و مقدار تازه را کم می‌کند؛ هر دو در یک تراکنش.
  • قیدهای یکتا، مسابقه را حل می‌کنند. دو کارگر که همزمان ثبت یک روز را بفرستند، با ON CONFLICT (flock_id, date) DO UPDATE به یک ردیف می‌رسند.
  • صف آفلاین، دوبار ثبت نمی‌شود. هر عملیات clientId دارد و نتیجه‌اش در sync_receipts ثبت می‌شود؛ ارسال دوباره «duplicate» می‌گیرد نه ردیف دوم. حداکثر ۱۰۰ عملیات در هر ارسال (ArrayMaxSize(100)).
  • ریسک باقی‌مانده: ویرایش همزمان تنظیمات/گله آخرین‌نویسنده را می‌برد (ستون نسخه نداریم). برای تنظیمات یک مزرعه پذیرفتنی است؛ اگر روزی ویرایش همزمان گله مسئله شد، version و شرط WHERE version = ? اضافه می‌شود.

۸٫۳٫۳. هزینه کوئری: N+1 شناخته‌شده

analytics/overview برای هر گله جدا کوئری می‌زند. با F گله (A گله فعال):

۲ کوئری ثابت (تنظیمات مزرعه، فهرست گله‌ها)
+ ۴ کوئری به ازای هر گله (ثبت روزانه، هزینه، فروش، وزن)
+ حدود ۲ کوئری به ازای هر گله فعال (واکسن، دارو)

یعنی برای ۲۰ گله (۱۲ فعال) حدود ۱۰۶ کوئری؛ امروز با ۲ گله، پاسخ در ۱۶ تا ۲۴ میلی‌ثانیه روی همین محیط اندازه‌گیری شد. رشد خطی است: تا چند ده گله مشکلی نیست، برای صدها گله باید یک کوئری تجمیعی (یا کش کوتاه در Redis) جای چهار کوئری تکراری بنشیند. این کار عمداً به فاز Redis سپرده شده چون درست‌کردنش بدون کش، پیچیدگی SQL را زیاد و سود کمی می‌دهد.

۸٫۳٫۴. مقیاس افقی

  • API بی‌حالت است (JWT، بدون نشست سروری) → پشت بالانسر، هر تعداد نمونه، بدون چسبندگی نشست.
  • استخر اتصال: PG_POOL_MAX با پیش‌فرض ۱۰ به ازای هر نمونه (db/database.ts). با ۵ نمونه یعنی حداکثر ۵۰ اتصال به Postgres — زیر سقف رایج ۱۰۰.
  • docker-compose.yml هر سرویس را با healthcheck و restart: unless-stopped بالا می‌آورد؛ API مهاجرت‌ها را پیش از پذیرش درخواست اجرا می‌کند.
  • PGlite فقط برای توسعه و تست است (یک نویسنده، درون فرایند). تولید با PG_DRIVER=postgres می‌رود و همین رفتار SQL را دارد، چون آزمون‌ها هم روی موتور واقعی Postgres اجرا می‌شوند.
  • Redis در compose بالا می‌آید و اکنون محدودسازی نرخ از آن استفاده می‌کند؛ کش شاخص‌ها و صف اعلان هنوز باقی‌اند (فاز بعد).

۸٫۳٫۵. برآورد ظرفیت

بار نوشتن ذاتاً سبک است: هر سالن روزی یک ثبت (تلفات، دان، آب) و چند وزن‌گیری. برای ۱٬۰۰۰ مزرعه با ۲ سالن فعال: حدود ۲٬۰۰۰ ثبت در روز ≈ ۰٫۰۳ درخواست بر ثانیه. گلوگاه واقعی، خواندنِ داشبورد است (بازخوانی overview) و همان N+1 بالا. نتیجه: معماری امروز با یک نمونه API و یک Postgres، بار چند صد مزرعه را با حاشیه زیاد تحمل می‌کند؛ برای هزاران مزرعه، کش و تجمیع کوئری لازم است — نه تغییر معماری.

۸٫۵. حدودی که پذیرفته‌ایم

  • تک‌مستأجری در هر نشست: یک کاربر در هر لحظه یک مزرعه فعال دارد (switch-farm برای جابه‌جایی است). داشبورد «همه مزرعه‌ها در یک نما» نداریم.
  • بدون ۲FA و بدون ورود با شماره پیامکی: عمداً؛ هزینه پشتیبانی‌اش برای مزرعه کوچک توجیه ندارد.
  • PGlite در تولید ممنوع: عمداً فقط توسعه/تست.
  • بدون ریزخدمت: یک API یکپارچه (modular monolith). جداکردن سرویس تحلیل، تنها جداسازی است و دلیلش هم بار CPU متفاوت مدل‌های ML است.
  • گزارش‌ها در حافظه ساخته می‌شوند: برای حجم یک دوره (≤۶۰ ردیف) کافی است؛ برای آرشیو چندساله به ذخیره‌سازی فایل (S3) نیاز داریم — فاز S3.
